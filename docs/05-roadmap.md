# 05 — Roadmap (honest, value-at-every-phase)

Building an OS from scratch is multi-year. The cardinal rule of this roadmap: **deliver something real and useful at the end of every phase**, so the project never depends on a distant, all-or-nothing 1.0. Each phase is a usable artifact, not just a milestone.

## Phase 0 — "It boots and talks to itself" (the kernel proof)
**Goal:** Mansa microkernel boots in QEMU (AArch64), creates address spaces and threads, and two userspace processes exchange a capability-secured IPC message.
- Mansa core: MMU, scheduler, capabilities, IPC channels.
- AfriIDL v0 + code generator.
- Hermetic Cargo build → bootable image; emulator-first CI.
- **Deliverable:** a real microkernel you can boot and demo. Tiny, but it's the spine.

## Phase 1 — "A computer, not yet a phone" (userland + graphics)
**Goal:** Mansa hosts real services and draws to a screen in the emulator.
- Asili driver framework + stable ABI; first virtual drivers (display, input, storage, virtio-net).
- Core services: Device Manager, Display Server (Tonga/Vulkan), VFS+CoW FS, Netstack.
- Sankofa UI v0 renders a declarative app; a shell/launcher.
- **Deliverable:** AfriSovera boots to a graphical shell in QEMU and runs a native demo app.

## Phase 2 — "It has apps" (the app gap, addressed)
**Goal:** All three app classes run. *This is the existential phase.*
- **Nia** WASM/WASI runtime + AfriSovera SDK GA (Sankofa UI + AfriCore APIs) for multiple languages.
- **Web/PWA** runtime integrated — existing web apps run.
- **Daraja** Android-compat bridge: first real Android apps running boxed.
- AfriStore v0 (WASM + PWA + bridged Android), signature-verified.
- **Deliverable:** a developer can build a Nia app *and* a user can run web + Android apps — all in the emulator. The OS is now genuinely useful before any phone exists.

## Phase 3 — "It runs on real silicon" (the driver gap, addressed)
**Goal:** Boot on physical hardware.
- SBC bring-up first (Raspberry Pi / PINE64) — open-ish hardware we control.
- Asili **Android-driver shim** for a reference phone: real GPU, Wi-Fi, sensors, then modem/cellular + multi-SIM.
- Power Manager + ration mode; atomic A/B updates with rollback.
- **Deliverable:** AfriSovera boots and is daily-driveable on at least one real device, with a published device-support tier list.

## The PC track — x86-64 PCs and laptops are a full target (owner's decision, 3 Nov 2026)
**Why:** device ownership means *every* device the owner bought, and the PC is where most people
meet the corporate lock-in hardest. Until this decision x86-64 was "emulator/dev path only"
([`01`](01-kernel-mansa.md)); it is now a first-class target beside ARM phones, and it runs as a
**parallel track from now on**, not after Phase 3. The same Nia (WASM) apps run unchanged on both,
which is what makes phone + PC one ecosystem rather than two products.

Why it is tractable: a PC is the most *open* real machine there is — UEFI firmware, standard,
publicly documented parts (no secret SoC drivers), and it boots from a USB stick without touching
the installed system. The cost is a second CPU architecture in the kernel.

PS/2 mouse and laptop touchpads (in their PS/2-compatible mode) DONE 7 Nov 2026 (suite 725 `pc-ps2mouse`): the i8042's aux port moves the same pointer as the USB mouse, so window drags and dock clicks work from a laptop's own touchpad. Intel HD Audio (7 Nov 2026, suite 726 `pc-hda`): the PC's own sound chip -- controller reset, codec commands over CORB/RIRB, the best analog output pin (speaker, headphones, line out) followed to its DAC, 44.1 kHz stereo from a ring refilled behind the DMA; `audio tone`, `say` and Nia's `speak()` use it when there is no virtio-sound, and `lshda` shows the controller, codec and path. Intel's newer wired chips (7 Nov 2026, suite 727 `pc-igb`): the I210/I211 on most desktop boards since 2013 and the 2.5 GbE I225/I226 since 2019 (igb/igc family) share the e1000 driver with advanced descriptors and queue registers; proved on QEMU's 82576 (DHCP, ping, TCP); the I225/I226 are driven the same way but not yet tried on real hardware. Realtek wired chips (7 Nov 2026, suite 728 `pc-rtl`): the RTL8111/8168 on most consumer desktop boards and laptops, with its RTL8101 and RTL8169 siblings (Linux r8169), share the RTL8139C+'s descriptor rings, so `pc/rtl8169.rs` is proved on QEMU's RTL8139C+ (DHCP, ping, TCP) and differs for the real chips only in the poll and link registers; `lsrtl` shows it. Not yet tried on a real RTL8168 (Linux carries extra per-revision start-up settings; the firmware's PHY set-up is trusted); the RTL8125 2.5 GbE is not claimed. SD card readers (7 Nov 2026, suite 729 `pc-sdhci`): a laptop's SD slot on a standard SD Host Controller (SDHCI: Intel, O2 Micro/BayHub, Ricoh) -- the SD start-up sequence, standard (SDSC) and high-capacity (SDHC/SDXC) cards, one block at a time through the controller's data port; `lssd` shows it, and a blank card holds AfriSovera's files after `claimdisk sd` (a camera or phone card, or one with its write-protect switch on, is never written). Proved on QEMU's sdhci-pci with an 8 MiB SDSC and a 4 GiB SDHC card. Realtek's own PCIe card readers (RTS52xx) are not SDHCI: `lssd` names them, not driven. The PC's power button (7 Nov 2026, suite 730 `pc-powerbutton`): a short press is ACPI's fixed power-button event; the kernel finds its registers in the FADT, switches the chipset into ACPI mode if the firmware has not (ACPI_ENABLE to SMI_CMD, as Linux does) and arms the button, and a press then saves the shell's files to the disk in use and switches the PC off through the firmware -- before, a real PC's button either did nothing or cut the power without saving. `acpiinfo` shows it. Proved on QEMU's q35 (OVMF already leaves ACPI mode on, so the switch-over itself waits for a real PC); laptops whose button is an ACPI control-method or hardware-reduced device need ACPI's AML and are reported, not handled. PCs with more than one USB 3 controller (7 Nov 2026, suite 731 `pc-xhci2`): AMD boards and recent Intel laptops have several xHCI controllers, and on the laptops the USB-C/Thunderbolt one (00:0d.0) comes before the one with the USB-A ports (00:14.0), so the driver, which took the first found, would never see a keyboard or stick there; each controller is now taken from the firmware, reset and looked at, and the first with a device plugged in is driven (one controller at a time; the others are left switched off). Proved on QEMU with two controllers, the keyboard on either. On Intel 7/8/9-series chipsets (2012-2015 PCs) the ports can also be left wired to the older EHCI (USB 2) controller, which AfriSovera does not drive: as Linux does, every port the chipset allows is switched to the xHCI first (XUSB2PR/USB3_PSSEN), with one boot line saying what moved -- QEMU has no Intel xHCI, so that waits for a real PC. Several controllers driven AT ONCE (7 Nov 2026, suite 732 `pc-xhci-multi`): every controller with a device plugged in at power-on now runs, each with its own command ring, event ring and device table, so a keyboard on one and a USB stick on another both work (and `lsusb` lists each controller with its devices); proved on QEMU with the keyboard and the stick on two controllers, then swapped, the stick keeping a file across the power-off. Hot-plug on EVERY controller (7 Nov 2026, suite 733 `pc-xhci-hotplug`): a controller with nothing in it at power-on now runs too ("nothing yet: for hot-plug"), so a keyboard or stick plugged later into any USB port is seen, as on Linux; proved on QEMU with two empty controllers, a keyboard plugged into the second, then the first, typed on and unplugged each time. Hot-plug BEHIND a USB hub (8 Nov 2026, suite 734 `pc-usbhubplug`): hubs were read once at power-on, so a device plugged into a desk hub, a monitor's USB ports or a laptop dock later was never seen; now each hub's status-change endpoint runs, and a port it reports is served like a root port (a new device reset and enumerated with its route string and transaction translator, a gone one detached with everything behind it); `lsusb` counts the hubs watched. Proved on QEMU with an empty hub: a keyboard plugged into it, typed on and pulled out, then a second hub plugged into it and a keyboard into that (two tiers), typed on, and both pulled out again. Touchscreens, graphics tablets and remote-console mice (8 Nov 2026, suite 735 `pc-usbtablet`): an all-in-one PC's or touch monitor's USB touchscreen, a drawing tablet, and the absolute mouse of a server's remote console (KVM/BMC) or a virtual machine are not boot mice, so the driver used to leave them alone; it now reads such a device's HID report descriptor, finds its absolute X and Y and its buttons (or a touchscreen's tip switch, used as the left button), and puts the pointer where the device says -- a tap lands where it touched, window drags and dock clicks work as with a mouse; `lsusb` and `devices` list it. Proved on QEMU's usb-tablet (pointer placed, clicked there twice, placed again, drawn on the screen); the parser was also checked on a typical single-touch touchscreen's descriptor (report ID, tip switch, 12-bit X/Y). Not yet tried on a real touchscreen; multi-touch panels give their first finger only. Internet from an Android phone over its USB cable (8 Nov 2026, suite 736 `pc-usbtether`): most phones' "USB tethering" is RNDIS (Microsoft's Remote NDIS), not the CDC-ECM that USB Ethernet dongles speak, so a phone plugged in was not a network; the USB network driver now also speaks RNDIS (start-up and the MAC address through RNDIS control messages, each frame wrapped in RNDIS's packet header, several frames per transfer accepted), so DHCP, ping and TCP run over the phone's mobile data. A device that offers both is driven as CDC-ECM, as on Linux. Proved on QEMU's usb-net in its RNDIS configuration; not yet tried on a real phone, and phones that tether with the newer CDC-NCM are not yet driven (QEMU has no CDC-NCM device to prove it on). USB headsets and speakers (8 Nov 2026, suite 737 `pc-usbaudio`): the cheapest sound a PC can have, and the only one on many thin clients and desks, was "audio, not driven"; the USB driver now reads a USB Audio Class 1.0 device's playback settings (16-bit PCM, stereo before mono, 44.1 kHz before 48 kHz), switches it on, unmutes it and feeds its isochronous endpoint one packet per millisecond, resampled from the shared 44.1 kHz sound; `audio tone`, `say` and Nia's `speak()` play through it when one is plugged in, before the PC's own HD Audio chip, as other systems switch to a newly plugged headset. Proved on QEMU's usb-audio by the sound file it wrote (the 441 Hz tone and the speech, every packet played, none missed). Not yet tried on a real headset; Audio Class 2.0 devices (many USB DACs) are named, not driven; the microphone side is not driven. A USB serial cable as the console (8 Nov 2026, suite 738 `pc-usbserial`): no PC sold in years has a COM1 header, so on real hardware the boot log and the shell were on the screen only, with nothing to copy from when bring-up goes wrong; the USB driver now drives FTDI USB-to-serial chips (FT232R, FT232H, FT2232, FT4232, FT-X: the chip in most cheap cables), sets the line to 115200 8N1 as COM1, mirrors every console line to the cable and passes what is typed on its far end to the shell, so a second computer with any terminal program sees the PC's log and can type commands; `lsusb` and `devices` list it. Proved on QEMU's usb-serial (an FT232): commands typed on the cable ran and their output came back on it. Not yet tried on a real cable; CH340, PL2303, CP210x and CDC-ACM cables are not driven yet (QEMU has none of them). The built-in eMMC disk of cheap laptops and tablets (8 Nov 2026, suite 739 `pc-emmc`): most low-cost Celeron, Pentium Silver and Atom laptops have no SATA or NVMe disk at all but 32-128 GB of eMMC soldered on the board, on the same SD Host Controller as an SD slot; the SD driver now also speaks the MMC start-up (CMD1, the host-given address, EXT_CSD for the real size of a sector-addressed chip, its eMMC version and boot partitions), ignores the write-protect pin (a soldered chip has none), does not wait for "card inserted" on an embedded slot, and tries every SD controller in turn (a laptop's empty SD slot is often found before its eMMC). The user area is used, never the boot partitions, and the same safety rule holds: a blank eMMC holds AfriSovera's files only after `claimdisk emmc`, one holding Windows or anything else is left alone. Proved on QEMU's emmc: a 4 GiB sector-addressed chip claimed, written and read back after a power-off, and a 64 MiB byte-addressed chip with two boot partitions and data on it named, refused and left byte for byte the same. Not yet tried on a real laptop's eMMC; it runs one block per command through the controller's data port (no DMA, multi-block or HS200 yet). The partition tools see it (8 Nov 2026, suite 740 `pc-installdisk-emmc`): `lsparts`, `installdisk emmc`, `installpart`, `formatpart emmc`, `tablebackup`, `tablerestore` and `bootplan` work on an eMMC-only laptop, and AfriSovera's partition in its GPT is used at every boot. A faster bus (8 Nov 2026, suite 741 `pc-sdbus`): after start-up a card or eMMC no longer stays on 1 data line at <= 25 MHz (about 1 MB/s at best): SD cards get the 4-bit bus and, when the slot can, high speed (50 MHz); an eMMC gets the 8-bit bus when the slot is wired for it, else 4-bit, and 52 MHz high speed when it offers it; a block read before the change is read again after it, and if it differs card and slot go back to the slow bus that worked. Proved on QEMU (SD card 4-bit at 26 MHz -- that controller's clock divider cannot make 50 -- and eMMC 4-bit at 52 MHz, files written and read back after a power-off); not yet timed on a real laptop, and the 8-bit bus waits for a real slot that offers it. Multi-block reads (8 Nov 2026, suite 742 `pc-sdmulti`): a read that is not already in memory fetches up to 16 blocks in one command (CMD18, the controller ending it with Auto CMD12) and the next reads are served from that copy, so loading the files at start-up takes 3 commands instead of 43; switched on only after the first 8 blocks read that way equal the same blocks read one at a time, and `lssd` counts the reads. Multi-block writes (8 Nov 2026, suite 743 `pc-sdwrite`): the files are saved in order, one block after another, so the driver now gathers such a run (up to 16 blocks) and sends it with one command (CMD25, ended by Auto CMD12) when the run ends or before anything else reaches the card; the first such write is read back block by block and must be equal, else it is rewritten one block at a time and multi-block writes stay off. Saving the files now takes 4 commands instead of 49 (proved on QEMU's SD card and eMMC, files back after a power-off); `lssd` counts the writes. There is no DMA yet.*

5. **Install alongside / instead of the old OS**, with a backup of the original first.
   *Groundwork DONE 6 Nov 2026 (suite 709 `pc-gpt`): `lsparts` reads the internal disks' partition tables READ-ONLY
   (GPT with both headers and the entry array CRC-checked, or old MBR), names Windows/Linux/EFI partitions and finds
   the free space; a damaged table is flagged "not safe to change". `installplan` (suite 710 `pc-installplan`, 6 Nov 2026)
   says where AfriSovera's partition would go (biggest 1 MiB-aligned free space, a free table entry) or why not, and
   never plans to resize another system's partition. `tablebackup` (suite 711 `pc-tablebackup`, 6 Nov 2026) copies every
   internal disk's partition table (GPT: both headers and entry arrays; MBR: sector 0) to a USB stick, read back and
   CRC-checked, and `tablecheck` compares that copy with the disk now. `installpart <disk> <MiB>` (suite 712 `pc-installpart`, 6 Nov 2026) is the first and only command that writes an internal disk: it adds AfriSovera's empty partition as one new GPT entry where the plan says (both GPT copies, both CRCs, read back), and only when the table is healthy, the USB stick's backup matches the disk now and the owner types the 4-digit code the plan shows (tied to the table as it is). `tablerestore <disk>` (suite 713 `pc-tablerestore`, 6 Nov 2026) is the way back: it writes the table saved on the stick back onto its disk (only the sectors that differ, backup GPT copy first) on the owner's code, and `tablebackup` keeps a copy taken before a change unless the owner types `tablebackup new`. `formatpart nvme` (suite 714 `pc-formatpart`, 6 Nov 2026) formats that partition on the owner's code and keeps the shell's files inside it from then on; at every boot the NVMe driver finds it again in a healthy GPT, and nothing outside it is written. `formatpart sataN` (suite 715 `pc-formatsata`, 6 Nov 2026) does the same on a SATA disk; the AHCI driver finds the partition at every boot. MBR disks are not changed yet. **`installdisk nvme|sataN`** (suites 716 `pc-installdisk` and 717 `pc-installdisk-sata`, 6 Nov 2026; both PASS in the cloud walk of a98fd19, 717/717) is for a PC that is AfriSovera's alone (the owner's spare PC): it shows what is on the disk, warns that EVERYTHING is erased, and on the owner's code writes a fresh GPT -- an EFI system partition (FAT32, 300 MiB) holding EFI\BOOT\BOOTX64.EFI, the very file the kernel was started from (read through the firmware before boot services exit), and AfriSovera's partition (the rest, formatted, the shell's files kept there). The PC then starts AfriSovera from that disk with no USB stick (proved in QEMU with only the NVMe disk attached). Booting from a partition next to Windows (an EFI boot entry) is next: `bootentries` (suite 718 `pc-bootentries`, 7 Nov 2026) shows the firmware's boot entries READ ONLY (BootOrder, each Boot#### with where it points, the one started from, the next free number, whether AfriSovera has one), read once before boot services exit; adding AfriSovera's own entry comes after, on the owner's word. `bootplan` (suite 719 `pc-bootplan`, 7 Nov 2026) says READ ONLY where it would go: each internal disk's EFI system partition checked as FAT32 (boot sector, both FAT copies equal, closed cleanly -- not after Windows Fast Startup or a crash), what \EFI holds, the free room, the boot file planned as \EFI\afrisovera\afrisovera.efi if it fits, and the next free Boot#### added at the END of BootOrder so the PC keeps starting Windows first. `bootcopy` (suite 720 `pc-bootcopy`, 7 Nov 2026) then copies the boot file there on the owner's code: only free clusters, their FAT entries in both copies, two free slots of \EFI (long names) and FSInfo's count are written, nothing already in the partition is moved or changed, and it is read back byte for byte; `bootcopy remove` is the way back (both FATs and FSInfo exactly as before). `bootentry` (suite 721 `pc-bootentry`, 7 Nov 2026) then adds AfriSovera's own firmware boot entry on the owner's code: one Boot#### "AfriSovera" pointing at that file in that partition (by its GPT GUID), added at the END of BootOrder so the PC keeps starting Windows first and AfriSovera is picked from the firmware's boot menu; both variables are written through the firmware's runtime services and read back, and the suite proves the entry is still there at the next power-on. `bootentry remove` is the way back (BootOrder as before, the entry deleted). `bootnext` (suite 722 `pc-bootnext`, 7 Nov 2026) is that proof: on the owner's code it sets BootNext to AfriSovera's entry, and at the next power-on the firmware itself starts AfriSovera from the Windows EFI partition ONCE (the boot stick still plugged in and first in BootOrder), deletes BootNext, and the power-on after that starts the usual first choice again. `fwinfo` (suite 723 `pc-fwinfo`, 7 Nov 2026) says READ ONLY which firmware started AfriSovera (vendor, revision, UEFI version), whether its variable services answer, and whether Secure Boot is on (SecureBoot, SetupMode), with one plain line for the owner: switch Secure Boot off first, or the firmware can start AfriSovera from its own entry; proved on edk2 without Secure Boot (not reported) and with Secure Boot built in and no keys (off, setup mode). Next: the owner's real-PC try (run `fwinfo` first).*

## Phase 4 — "It's sovereign" (AfriCore + distribution)
**Goal:** the differentiated, emerging-market product.
- **AfriPay** (first country's M-Pesa/MoMo + USSD + system payment sheet), **AfriShare** P2P, **AfriPush**, **AfriID** (self-hostable).
- **AfriStore** with local-currency payouts via AfriPay + offline P2P install.
- **Asili** on-device AI (translation, TTS/STT, low-literacy support).
- Native Asili drivers begin replacing Android shims, device by device.
- **Deliverable:** the OS does what iOS/Android don't for our users, with sovereign identity/payments/distribution.

## Phase 5 — "It's trustworthy & it scales" (hardening + reach)
- Verified boot hardening; pursue the **seL4-style formal verification** stretch goal on Mansa's core.
- Security audits; repair-kiosk flashing toolkit; partner-certified device program.
- Federated AfriID/AfriStore for sovereignty partners (telcos, states, universities).
- **Deliverable:** AfriSovera 1.0 — shippable on certified phones, with a real (if young) app ecosystem and a sovereign services stack.

## Team & funding shape (so it survives)
- **Core platform** (Rust kernel/drivers/IPC) — the scarce, expensive heart.
- **Graphics/UI** (Tonga compositor, Sankofa UI).
- **Runtimes** (Nia/WASM, Web integration, Daraja).
- **Services & payments** (AfriCore, AfriPay — regulated, per-country legal).
- **Device enablement** (bring-up, driver shims, tier validation).
- **Security** (capabilities, verified boot, audits, verification).
- **Funding:** sovereignty partners (telcos/states/universities) + AfriStore/AfriPay revenue. Phase 0–2 produce a fundable, demoable emulator OS long before hardware costs hit.

## The non-negotiables (kill criteria)
If any of these fails, the project is not viable and we should stop honestly:
1. **Apps run** (Web + Daraja by Phase 2) — or the OS is dead on arrival.
2. **Real hardware lights up** (driver shim path by Phase 3) — or it's a forever-emulator demo.
3. **Funding survives the multi-year build** — or scope down to an emulator/SBC developer platform and ship *that* as the product.
