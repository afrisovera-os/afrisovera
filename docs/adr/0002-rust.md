# ADR 0002 — Rust for the kernel, drivers and services

- **Status:** Accepted
- **Date:** 2026-08-05 (Phase 0, commit `29f18b3`)
- **Deciders:** owner; recorded by the chief architect 2026-11-08
- **Related:** ADR 0001 (microkernel), docs/01-kernel-mansa.md, docs/04-the-toolchain.md

## Context

An operating system's trusted computing base is where memory-safety bugs become privilege escalation.
Industry data (Microsoft MSRC, Google Chrome and Android security teams) puts memory-safety defects at
roughly 70 % of serious CVEs in C/C++ systems code. AfriSovera is written by a very small team, much of it
AI-assisted, with no separate security-audit budget; the language must catch whole classes of defect at
compile time rather than relying on review. The kernel must run with no garbage collector, no runtime, and
predictable latency, on AArch64 and x86-64, and be able to call firmware (UEFI) and touch MMIO directly.

## Decision

Mansa, every Asili driver, the AfriCore services and the AfriSh shell are written in **Rust**, `no_std`,
with the toolchain pinned in `rust-toolchain.toml`. `unsafe` is permitted only at hardware and ABI
boundaries (MMIO, DMA descriptors, page tables, context switch, firmware calls, the syscall entry) and
each `unsafe` block states the invariant it relies on. Assembly is limited to entry stubs, vectors and
context switch (`global_asm!`).

Applications are **not** required to be Rust (ADR 0003): any language that compiles to WebAssembly is
first-class.

## Consequences

Good:
- Use-after-free, double free, out-of-bounds and data races are compile errors outside `unsafe`.
- One language from boot stub to shell keeps the codebase reviewable by one person.
- Cargo gives hermetic, reproducible builds; `cargo build` is the whole build for both architectures.

Bad / accepted costs:
- Fewer kernel engineers know Rust than C; contributor pool is smaller.
- `no_std` excludes most of crates.io; the project carries its own SHA-256/512, Ed25519, heap allocator,
  font and TCP/IP stack (`kernel/src/sha256.rs`, `sha512.rs`, `ed25519.rs`, `heap.rs`).
- Compile times are long; heavy builds and the full test walk run on CI runners, not on developers' machines.
- `unsafe` at driver boundaries is still where bugs live; Rust narrows the search, it does not end it.

## Evidence in the tree

- `kernel/Cargo.toml` (`license = "Apache-2.0"`, `no_std` binary), `rust-toolchain.toml`.
- Both kernels (ARM `kernel/src/main.rs`, PC `kernel/src/pc/main.rs`) are Rust; the only non-Rust code is
  `global_asm!` entry/vector stubs.
- A Rust user program compiled for EL0/ring 3 (`kernel/src/rustapp.bin`, `kernel/src/pc/rustapp-x86_64.bin`).

## Alternatives considered

| Option | Why not |
|---|---|
| C (seL4, Zircon, Linux style) | The defect class we most need to remove is exactly what C allows. |
| C++ with a safe subset | Safety by convention, not by compiler; no ecosystem for `no_std` freestanding use. |
| Zig | Good freestanding story, but not memory-safe and pre-1.0 when chosen. |
| A managed language (Go, C#) | GC pauses and a runtime in the kernel; not acceptable for interrupt paths. |

## Revisit if

- A required target has no maintained Rust backend (none known today: AArch64 and x86-64 are tier 1/2).
- `unsafe` lines exceed ~10 % of kernel lines, which would mean the safety argument has thinned out.
